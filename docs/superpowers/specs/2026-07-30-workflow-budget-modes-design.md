# Workflow 流程预算模式设计

## 目标

用轻量级、中量级、重量级和自动判断 4 种模式替代现有的轻量级、完整模式以及 `Trivial / Standard / Complex` 分级。新机制以 Superpowers 流程预算为核心：轻量级优先速度，中量级平衡速度与质量，重量级完整执行所有适用流程，自动判断则在每个任务开始时临时选择其中一个固定档位。

模式预算必须在任务开始时约束流程规划，不能先机械执行完整 Superpowers 流程，再在配额耗尽后停止或报告无法继续。

## 范围

- 将新对话的默认模式改为自动判断。
- 提供 `$workflow-auto`、`$workflow-light`、`$workflow-medium` 和 `$workflow-heavy` 4 个模式 Skill。
- 新建共享策略规则，集中定义预算、自动路由、计数口径、优先级和异常处理。
- 删除有效规则中的 `Trivial / Standard / Complex` 分级。
- 移除 `$workflow-full` 与 `[模式：完整]` 旧入口，以重量级入口替代。
- 保留现有 HITL、Git、CodeGraph、Editor MCP、能力恢复、数据与外部副作用等不可绕过规则。
- 仓库验证通过后，将本任务修改的非 `global/root/` 文件同步到本机全局配置。
- 不改写历史规格和历史实施计划中的旧术语。

## 模式状态

### 默认状态

新对话默认进入 `$workflow-auto`。自动模式在每个新任务开始时重新判断执行档位，不把判定结果保存为固定模式。下一个任务必须重新判断。

自动模式每次输出一行判定结果和一句核心理由，例如：

```text
[自动模式 -> 中量级] 涉及多文件行为修改，需要有限设计与回归验证。
```

自动模式可以在任务中途因新发现的范围或风险升级，但不能自动降级。升级前已经使用的 Agent、测试和澄清轮次计入新档位的累计用量。升级只需告知用户，无需等待批准。

### 手动锁定

用户显式调用固定模式 Skill 或使用对应标签时，将当前对话持续锁定到该模式：

| 模式 | Skill | 标签 |
|---|---|---|
| 自动判断 | `$workflow-auto` | `[模式：自动]` |
| 轻量级 | `$workflow-light` | `[模式：轻量]` |
| 中量级 | `$workflow-medium` | `[模式：中量]` |
| 重量级 | `$workflow-heavy` | `[模式：重量]` |

单独调用模式指令时，只确认切换结果。模式指令与任务正文出现在同一消息时，先切换，再按新模式执行任务。最新的显式切换优先；任务中途切换只影响尚未完成的步骤，不撤销已有修改、验证或授权。

手动锁定后不再执行自动判断，直到用户显式切回自动模式。手动固定模式不会因任务复杂度自动升级或降级。

## 组件职责

### `global/AGENTS.md`

- 声明新对话默认使用 `$workflow-auto`。
- 声明模式 Skill 和开发流程触发时必须加载共享流程策略。
- 保留全局回应风格、HITL、Git、CodeGraph、Editor MCP、能力恢复和外部副作用等规则。
- 不承载详细预算矩阵，避免全局入口继续膨胀。

### 模式 Skill

- `workflow-auto` 负责逐任务路由、判定通知和任务中途升级。
- `workflow-light`、`workflow-medium`、`workflow-heavy` 负责显式切换和持续锁定。
- 4 个 Skill 只保存模式状态与入口行为，具体流程预算统一引用共享策略。
- 只有 `workflow-auto` 允许隐式调用；其余 3 个固定模式只允许显式调用。

### `global/rules/workflow-policy.md`

该文件是流程预算的单一事实来源，包含：

- 3 个固定档位的预算矩阵。
- Superpowers 各阶段的裁剪方式。
- 自动路由条件与升级规则。
- Agent、测试和澄清轮次的计数口径。
- 用户显式要求、固定模式、自动模式与 Skill 默认流程之间的优先级。
- 配额不足、环境故障和不可绕过规则冲突时的处理方式。

## 流程预算

| 维度 | 轻量级 | 中量级 | 重量级 |
|---|---|---|---|
| 核心目标 | 速度优先 | 速度与质量平衡 | 完整性优先 |
| 可读写 Agent | 每个任务累计最多 1 个 | 每个任务累计最多 3 个 | Harness 不限制 |
| 只读 Agent | 每个任务累计最多 3 个 | 每个任务累计最多 5 个 | Harness 不限制 |
| 测试轮次 | 每个任务最多 1 次 | 每个任务最多 3 次 | Harness 不限制 |
| 澄清轮次 | 每个任务最多 3 次 | 每个任务最多 5 次 | Harness 不限制 |
| `brainstorming` | 必要澄清和简短方案确认 | 保留需求、方案和关键设计确认，合并往返 | 完整执行 |
| 规格文档 | 默认不生成 | 仅多文件、跨模块或存在关键契约时生成 | 按适用流程完整执行 |
| 实施计划 | 默认不生成持久化计划；复杂任务只维护简短任务清单 | 多步骤任务生成计划，可压缩非关键说明 | 按适用流程完整执行 |
| TDD | 不强制先写测试；选择信息量最高的验证 | 高风险逻辑优先 TDD，其余按风险选择 | 按适用流程完整执行 |
| 代码评审 | 主 Agent 检查 diff，不强制派发评审 Agent | 重要修改至少进行一次定向评审 | 按适用流程完整执行 |
| 最终报告 | 变更、验证证据和残余风险 | 变更、验证、评审和风险 | 完整交付记录 |

重量级的 Harness 不限制不代表无效消耗，也不突破平台并发、上下文容量或更高优先级规则。所有模式都只执行适用 Skill，不机械调用无关 Skill。

### Agent 计数

- 配额按单个任务内的累计派发数量计算，不按同时活动数量计算。
- 完成、失败、被中断或返工重新派发的 Agent 均占用额度。
- Agent 派发时必须冻结为只读或可读写身份；只读 Agent 不得在后续升级为写入。
- 子 Agent 不得继续派发下级 Agent，避免绕过累计配额。
- 平台并发上限独立生效。

### 测试轮次

- 一次测试轮次只能运行一个既有测试目标，例如一个测试文件、一个测试套件或一个项目测试脚本。
- 同一轮允许测试框架内部执行多个测试用例，但不得临时组合原本独立的测试目标以绕过配额。
- 修复后重新运行计为新的一轮。
- lint、类型检查、构建和测试框架执行计入测试轮次；`git diff`、只读搜索和纯静态内容检查不计入。
- 因工具、依赖或环境故障而未真正开始验证的调用不消耗额度，但必须保留失败证据。

### 澄清轮次

- 每次暂停并等待用户补充需求、范围或技术歧义，计为一次澄清轮次。
- Agent 应在任务开始时合并相关问题，采用有依据的低影响假设，并尽早进入执行。
- 澄清配额用于限制 Superpowers 的设计与规格往返，不能在机械执行完整流程后作为停止理由。
- 法律、安全、数据、外部副作用、Git 历史改写和 Editor MCP 等强制 HITL 不计入普通澄清配额，也不能因配额耗尽而跳过。

## 自动路由

自动判断采用高风险条件优先、默认中量级的规则树，不使用数字评分，也不重新引入用户可见的任务复杂度分级。

### 轻量级条件

只有同时满足以下条件时才选择轻量级：

- 目标明确，关键契约没有待确认项。
- 属于只读查询、解释、翻译、局部文档调整或范围明确的低风险修改。
- 修改范围局部，预计一次高价值验证足够。
- 不涉及安全、数据迁移、公共 API、共享基础设施、项目设置或显著外部副作用。
- 不需要完整规格、跨模块协调或多轮评审。

### 重量级条件

命中以下任一条件即选择重量级：

- 架构设计、跨模块重构或公共契约变更。
- 数据迁移、鉴权、安全、隐私、支付或不可逆外部副作用。
- Cocos、Unity 场景、资源或项目设置等需要严格 Editor MCP 流程的高风险修改。
- 任务包含多个相互依赖的子系统，或预计需要持续多轮实现与评审。
- 用户明确要求完整 Superpowers、完整 TDD、全面评审或最高可靠性。
- 中量级预算明显不足以完成必要验证。
- 失败可能造成严重的数据、生产或兼容性影响。

### 中量级条件

未命中重量级条件，也不同时满足全部轻量级条件时，默认选择中量级。常见任务包括常规功能开发、一般 Bug 修复、多文件但边界清晰的修改，以及需要有限设计、计划、测试或评审的任务。

### 中途升级

- 轻量级发现公共契约、跨模块影响或第二轮必要测试时，可以升级到中量级。
- 轻量级或中量级发现重量级风险时，可以升级到重量级。
- 自动升级必须展示新档位和一句原因，不等待用户确认。
- 手动固定模式不自动升级；只有不可绕过规则发生冲突时才进入 HITL。

## 优先级与覆盖

规则优先级从高到低如下：

1. 系统、平台、安全、数据、外部副作用和强制 HITL 规则。
2. 用户在当前任务中明确提出的执行要求或显式指定的 Skill。
3. 用户手动锁定的固定模式。
4. 自动模式为当前任务选择的临时档位。
5. Superpowers Skill 自身的默认完整流程。
6. Harness 的一般效率偏好。

用户显式要求某个 Skill 时必须执行。如果该 Skill 的必要步骤超过当前档位配额，只放宽与该 Skill 直接相关的预算，不改变对话的持续模式。任务开始时简短声明临时覆盖，无需额外批准；下一个任务继续使用原固定模式或自动模式。

## 异常处理

- Agent 必须在开始执行前分配测试、澄清和派发预算。
- 工具、连接、依赖或环境故障遵循全局能力恢复规则；未真正启动的测试不消耗轮次。
- 已经实际运行但失败的测试消耗轮次，后续优先依据现有证据修复。
- 自动模式预算不足时按路由规则升级。
- 手动固定模式发现范围扩大时，重新规划剩余预算，不自动升级。
- 固定模式下普通质量目标无法完全覆盖时，完成可安全完成的范围并明确残余风险，不能只以配额不足为由停止。
- 只有继续执行会违反不可绕过底线时，才通过 HITL 请求切换模式、缩小范围或停止。

## 验证

1. 验证新对话默认进入自动模式。
2. 使用代表性场景验证自动模式分别路由到轻量级、中量级和重量级。
3. 验证自动模式在不同任务间重新判断，临时结果不持久化。
4. 验证手动切换后持续锁定，并能通过 `$workflow-auto` 恢复逐任务判断。
5. 验证自动任务只升级、不降级，且升级产生简短通知。
6. 使用 Codex Skill 快速校验脚本验证 4 个模式 Skill。
7. 验证只有 `workflow-auto` 允许隐式调用，其余固定模式均禁止隐式调用。
8. 验证有效规则中不存在 `Trivial / Standard / Complex`、`$workflow-full` 和 `[模式：完整]`。
9. 检查 Git diff，确认没有混入或恢复用户已有的无关改动。
10. 仓库验证通过后，将本任务修改的非 `global/root/` 文件同步到本机全局配置。
11. 逐项比较仓库源与本机全局文件，并再次校验本机安装的 4 个 Skill。

## 风险

- 移除 `$workflow-full` 是有意的破坏性接口迁移，旧提示或旧对话需要改用 `$workflow-heavy`。
- 共享策略文件是单一事实来源；模式 Skill 必须可靠加载该文件，否则预算不会生效。
- 自动路由依赖文字规则，必须通过覆盖典型边界的场景验证降低误判风险。
- 轻量级和中量级会主动裁剪 Superpowers 默认流程，因此共享策略必须明确高于 Skill 默认流程、低于用户显式要求和不可绕过规则。
- `workflow-policy.md` 超过约 5,000 字符时，应按能力域拆分低频细则，主规则保留触发条件和核心预算。
